Deliverable

Management BI for finance and operations

The Analytics Department had four staff when we were given a broad assignment: to build a management BI solution from scratch for finance, activity, staffing and sickness absence. I designed almost all of the model behind the reports. Colleagues led content and visual design. I was the owner from about August 2025 until the solution was decommissioned around February 2026, responsible for monthly updates and for improvements after user tests.

My role

#
My work
I designed almost all of the semantic model, meaning the model behind the reports, and developed most of the data transformations in Power Query and about 80 to 90 percent of the DAX calculations. I chose a star schema after weighing alternatives, and I had the main responsibility for technical troubleshooting.
The collaboration
Colleagues led the selection of content, the visual design and the presentation, and built parts of the report under my technical guidance. I contributed to navigation, tooltips and report structure.

In operation until around February 2026, when new reports covered the need.

More on status
Use
In operation for about a year and a half. The dashboard was never meant to be permanent, because BI is the responsibility of another department. In autumn 2025 I helped that department with Power BI. When their new reports covered the need, the dashboard was taken down so that the figures kept one shared source.

Four subject areas with different data foundations

#

The subject areas measure different things. An accounting amount, an activity measure, a staffing volume and an absence percentage can share organisation and time without having the same data grain, meaning what one row stands for, or the same calculation rule. The model had to preserve these differences.

The sources and update routes made monthly operation demanding. A figure had to be tied to the period it actually described. I worked on calendar logic, organisational hierarchies and the combination of historical and current structures, so that a shared selection did not give the impression that all areas were equally up to date.

The assignment was broad and loosely specified. It had to become a model colleagues could build reports on and managers could use. Model size, maintenance and new requests competed for the same development capacity. When the model's limits put delivery at risk, I separated a larger modernisation of the model from ongoing extensions.

Model, calculations and user needs

#

Sharing dimensions, preserving grain

#

The four subject areas had to answer the same organisational selections, while each calculation kept its own definition.

I designed the model with shared dimensions for organisation and time and separate fact tables for each subject area. After considering snowflake patterns, I chose the star schema as the main pattern, because it suits Power BI and is easier to maintain. I also pointed out redundant descriptive fields in the fact tables and tightened the separation between facts and dimensions.

A clear separation of facts and dimensions makes it possible to share organisation and time without mixing units of measure or row levels. A snowflake schema would have added more lookups between the dimensions and moved complexity into relationships and filter paths.

Each subject area still needed its own calculations and checks.

Defining the base before the percentage

#

Sickness absence had to be comparable across selections of different sizes. An average of unit percentages gives small and large units equal weight.

I worked with explicit denominator logic, meaning the base the percentage is calculated from, and consistent scoping of the percentage measures in DAX.

Numerator and base must apply to the same selection. Then the weighting follows the base behind the figures, and the percentage can be explained all the way down to the calculation. A simple average of unit percentages answers a different question: how the units do on average, not how large the absence is across the whole selection.

The denominator becomes a business definition that has to be maintained together with the measure.

Improving what users actually met

#

I ran guided tests with real users, observed where they became unsure and collected feedback.

The feedback steered the targeted improvement rounds, which I ran in addition to the monthly updates.

Technical basis

#
What a shared filter context must preserve

Data grain describes what one row stands for. Before a relationship is used, both the key and the row level must be understood. If an organisational unit is linked to several historical versions without a clear time rule, a seemingly simple selection can give wrong totals.

A semantic model gives tables and calculations a shared business meaning. Here organisation, periods and scoping were central. I developed and debugged the logic for variances, ratios, accumulated values, year to date and DRG activity across the subject areas.

The inspected model has 21 tables, 20 relationships and 204 DAX measures with content. The figures describe the scope of the model, not its quality or effect.

Weighted percentage and missing base

In a combined percentage, numerator and base are summed before the division. A simple average of unit percentages gives the units equal weight, even though their bases differ. Both methods can be meaningful, but they describe different quantities.

In the fictitious example each row must have a known, non-negative base and a known numerator within that base. Missing values cannot be replaced with zero. When the combined base is zero, there is no percentage to show.

Newly written example. It shows the pattern, not the original code.

function pooledShare(rows) {
  let numerator = 0;
  let base = 0;
  for (const row of rows) {
    if (!Number.isFinite(row.numerator) || !Number.isFinite(row.base)) {
      throw new Error("Numerator or base is missing.");
    }
    if (row.base < 0 || row.numerator < 0 || row.numerator > row.base) {
      throw new Error("The values do not describe a valid base.");
    }
    numerator += row.numerator;
    base += row.base;
  }
  return base === 0 ? null : numerator / base;
}
