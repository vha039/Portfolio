Deliverable

Redesigning the forecasting architecture

The forecasting solution is meant to calculate patient volume, bed needs and capacity 14, 90 and 365 days ahead. In phase I I was responsible for architecture and integration and added several models, while a colleague developed the original XGBoost model and much of the data and variable work. In phase II I led and carried out the redesign on my own in one month, with coding agents. The new architecture brings preparation and run planning together, while each model is to keep its own behaviour. The redesign is complete. The forecasting solution is in development and not in production.

My role

#
My work
In phase I I designed the repository and the overall architecture, built the orchestration that connects data, variables, models, evaluation and output, and developed the automation around it. I added GAM modelling and rolling validation, implemented SARIMAX and contributed substantially to the XGBoost model. I also challenged target definitions and validation choices.
The colleague's work
A colleague developed the original XGBoost model, many of the variables and substantial parts of the data validation, cleaning and filtering, and worked with the data supplier.
Phase II: the redesign
I led and carried out the architecture redesign on my own over one month. Coding agents handled well-defined parts of the implementation, while I was responsible for direction, integration and review of the changes.

The redesign is complete. The forecasting solution is in development, not in production.

More on status
Effect
The redesign was meant to preserve model behaviour. It is not a measure of forecast accuracy.

Several run paths had to work together

#

The architecture was to change around an existing collaboration and an existing model flow. Configured behaviour had to keep its meaning, while preparation, execution and output gained a clearer shared ownership.

Patient volume and capacity needs require precise target definitions. The time the forecast is made, the information known then, and the time the result applies to must be kept apart. Otherwise a calculation that runs can answer a different question from the one the planner needs answered.

The implementation had several origins: the colleague's model and data work, my architecture and model work, and the coding agents' contributions. The repository is about 40,000 lines of R and Python, written by both of us and by coding agents. Everything had to be brought together in one architecture.

A successful model run, a comparable migration and a good forecast are different outcomes. I required time-aware validation, comparison with simple baseline models and acceptance criteria.

Responsibility for execution, scope, time boundaries and conformance

#

Centralising responsibility for execution

#

Several entry points and different execution patterns made it hard to keep model runs and further development together.

I brought preparation, run planning and modular execution together in the new architecture, with clear boundaries towards the model calculations.

Shared preparation and run planning gather responsibilities that otherwise had to be coordinated for each entry point. The model calculations keep their own assumptions.

The shared logic had to handle real differences between the model pipelines.

Simplifying the plan along the way

#

The redesign with coding agents started from a far too ambitious plan. It would have given a sound core architecture for a large company selling forecasts as a service, with a lot of infrastructure our codebase did not need.

I noticed it fairly early and stopped the implementation. Starting from the partly implemented code, I re-planned, designed a tightly scoped minimum viable product (MVP) and implemented it in full.

Much of the work already done was good and could be reused. The architecture should fit the project's actual needs.

Making time and target professional choices

#

A forecasting dataset can contain information that only became known after the time the forecast was supposed to be made.

I examined target definition, overlapping intervals, duplicates, length of stay, temporal leakage and consistency between variables and target, and added rolling validation.

A holdout test, meaning data held out from model fitting, must imitate the situation in which the forecast will be used. The definition of an observation and of the time boundary is therefore part of the model assessment. A random split can overlook that the model uses information it would not have had.

Comparing what the redesign was meant to preserve

#

A large architectural change can alter behaviour even when the new parts each run on their own.

I compared configured behaviour before and after the redesign on an explicit basis, instead of treating a successful run as proof that the solution had been preserved.

Values must refer to the same observations before they can be compared. Missing and duplicated rows are deviations in their own right, even when a total looks the same. Comparing only totals or default settings could have hidden such differences.

A limited comparison speaks only about its own basis.

Technical basis

#
Time of information and time of the outcome

For a forecast it must be clear when the calculation is made and when the outcome applies. Information registered later cannot simply be used to describe what the model would have known earlier.

There is also a difference between a known zero observation and an outcome that is not yet known. If they are mixed, both the training data and the error measure can take on a different meaning from the target description.

These were questions I raised in the target definition and validation.

Comparing the same observation

An observation needs an identity that makes it possible to know that the old and the new value refer to the same quantity. Before the figures are examined, the key set must be unambiguous and comparable.

In the fictitious example, duplicates, rows that exist on only one side, and different missing values are separated from numerical difference. Two missing values give no numerical comparison, and such a case must not become a successful numerical check.

A complete key set is only the beginning. A real comparison must also establish the sample, configuration, underlying data and calculation that produced the values.

What remains before operational use

Architecture makes development and comparison possible, but does not by itself decide whether a forecast should be put into use. Operational use requires an assessment of the underlying data, relevant baselines, suitable error measures and agreed expectations for follow-up.

The architecture also makes it easier to add and compare model families. SARIMAX is still being tested and evaluated as an alternative to the existing models.
